# 03 主会话的上下文：早点压缩、长稿子传路径、查找交给子代理

2026-11-24 · 涉及：`hooks/compact.ts`、`hooks/register.tsx`、`engine/src/config.ts`（`hubCompactK`）、`engine/src/commands/reply.ts`、`skills/hub/SKILL.md`、`reply.md`、`handoff.md`

## 背景

[02](02-slim-events.md) 精简了事件，这篇处理剩下的：主会话的对话本身一直在长。业界常说的三招：

- **压缩**（compaction）：把旧对话换成一段摘要。
- **按引用传递**（pass by reference）：大块内容放在文件里，对话里只放路径。
- **上下文隔离**（context isolation）：会返回大段内容的查找交给子代理，用完就扔，只带回结论。

前提是重要的状态都不在对话里：事情、问题、回复、规矩、判断记录都在 chief 的文件里（结构化笔记），所以对话可以放心压。

## 量现状

**压缩：** 这之前都是 Claude Code 快满时自动压：

| 时间 | 压缩前 | 压缩后 |
| --- | --- | --- |
| 第一次 | 96.7 万 token | 2.0 万 |
| 第二次（25 小时后） | 96.8 万 token | 2.4 万 |

两次之间调用了 1026 次模型，平均每次背着 53.8 万 token，一共读入 5.5 亿。

**回复稿：** 工作会话把整段稿子用消息发给主会话（21 条，平均约 1200 字，含说明），主会话再把正文写进草稿文件（平均 255 字）。比预想的小。

**查找：**

| 工具 | 次数 | 平均每次返回（字符） |
| --- | --- | --- |
| 读 Slack 里的文件 | 3 | 约 25 万 |
| 搜 Slack | 6 | 约 8 千 |
| 读 Slack thread | 9 | 约 7.6 千 |
| 读 Slack 频道 | 18 | 约 1.7 千 |
| 搜会话记录 | 33 | 约 1 千 |

合计约 94 万字符，都留在主会话里。

## 改了什么

1. **早点压缩**：插件（只在主会话所在的会话里）每分钟看一次，上下文超过 `hubCompactK`（默认 200，即 20 万 token）、而且闲了 2 分钟，就调 `$.session.compact` 压一次（和手敲 `/compact` 一样），压过半小时内不再压。不管谁触发的压缩（插件、自动、手敲），都在 `session.compact` 里给总结器加一段说明：状态都在 chief 的文件里不用留，只留还没聊完的话、答应了没做的、处理到一半的事件、Monitor 和 cursor。`chief config set hubCompactK 0` 关掉。
2. **长稿子传路径**：工作会话把回复稿写进 `~/chief/data/drafts/`，消息里只写「稿子：<路径>」。`chief reply add` 多返回稿子的行数、字数和开头 60 字；主会话只在会直接发出去（规矩是 auto）或太长（超过 6 行、400 字）时才打开全文把关，其余用户在面板上会看到。写不了文件的工作会话退回老办法。
3. **查找交给子代理**：主会话原来的规矩是「不用子代理」（为了干活一律开独立会话）。加一个只读的例外：搜 Slack、搜会话记录、读长文档交给 Agent 子代理，只带回几行结论（找到什么、在哪、关键原话）；干活仍然开独立会话。

## 预计

- 压缩：每小时约涨 3.8 万 token，20 万时压一次，大约每 5 小时一次；平均上下文从约 50 万降到约 11 万，每次叫醒便宜 4 倍多。这是三项里最大的。
- 传路径：约 1% 的上下文，小。做它是因为改动小，而且回复长的时候省得多。
- 子代理：取决于主会话会不会照做；读一次 Slack 文件就是几十万字符。

## 结果

（跑一天后补）要看：

- 压缩：一天压了几次、每次压前压后多大，平均每次调用的上下文。
- 压缩会不会让它变笨：「判断错了」、重复问同一件事、忘了答应过的事有没有变多。
- 传路径：工作会话有没有照新格式交稿；主会话打开了几次全文。
- 子代理：主会话有没有用子代理查；它自己直接跑的大查找还有几次。
