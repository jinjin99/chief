# 02 精简交给主会话的事件

2026-11-24 · 涉及：`engine/src/commands/events.ts`（`relatedOf`、`streamLine`）

## 背景

主会话的上下文里装了什么（上一次自动压缩以后，按字符粗算，去掉截图）：

| 内容 | 约占 |
| --- | --- |
| 收到的事件和通知 | 30% |
| 主会话自己写的命令（进展、回复稿用 heredoc 写进命令里） | 25% |
| 和用户的对话 | 20% |
| 命令的返回 | 10% |
| 搜 Slack 的结果 | 5% |

这些用过一次就没用了，却一直留着，每次醒来都重读。这篇先动第一项：事件。

## 量现状

近两天主会话收到的 373 条事件，按字段拆：

| 字段 | 占比 |
| --- | --- |
| `related`（引擎附上的：同一个人、同一段私信或 thread 里没了结的事情和开着的问题） | 37.8% |
| `text`（消息原文） | 27.6% |
| `reply`（回复回到哪） | 6.8% |
| 其余 | 27.8% |

占地方最多的不是原文，是引擎附上的提示。再拆 `related`：

- 211 条 Slack 消息里 145 条带了 `related`，平均 1.4 件事、2.4 个问题，约 900 字。
- 每件事带着完整的进展，每个问题带着完整的问题和建议。
- 140 条是因为同一段私信或同一个 thread，只有 5 条只因为「同一个人」。范围不是问题。
- **同一个 thread 来十条消息，同样的 900 字附十次**：145 条里 82 条和同一段对话 6 小时内的上一条完全一样。

## 改了什么

1. `related` 只带认得出是哪件事、哪个问题的：事情的编号、标题、状态、会话；问题的编号和问题本身（最多 150 字）。进展、建议不带，要看再 `chief thing list`、`chief ask show`。主会话用 `related` 只做两件事：这条接的是哪件事、有没有答掉哪个问题，这些够了。
2. 同一段对话（私信按频道，频道里按 thread）6 小时内和上一条带的一样，只写 `{"sameAs": N}`。记忆只在这次挂着的 Monitor 里，重新挂上就清空，第一条照样带全的，不怕主会话压缩过上下文后对不上。

没动的：

- `reply`：主会话会用到（GitHub 的 `reply.ref` 找仓库）。
- 原文截断（1500 字）：一半以上的事件原文本来就短，再截短收益小，还可能看漏。

## 结果

| | 事件流总字符 | `related` 占比 |
| --- | --- | --- |
| 改之前 | 36.0 万 | 38% |
| 只带编号、标题和问题 | 29.9 万（-17%） | 25% |
| 再加同一段对话不重复带 | 26.4 万（-27%） | 15% |

事件约占主会话上下文的 30%，所以对整个上下文大约是 -8%。

## 结论和没解决的

- 先量再改：直觉是原文最占地方，量出来是引擎自己加的提示。
- 「给 agent 的提示」要像给人的提示：够它认出来就行，细节留个入口让它按需去查（按需检索），重复的只说「同上」。
- 待看：主会话会不会因为看不到进展、建议而归错事情、漏关问题。跑一周看「判断错了」有没有变多。
- 下一步：主会话自己写的命令（25%）和定期压缩。
